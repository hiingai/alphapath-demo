## 0. 一句话结论

> 已按方案 **P0** 交付并在线上跑通：用户在对话里说过的信息，会被**确定性规则**变成一条结构化线索
> （身份 / 激活日 / 受养人 / 学段 / 诉求 / 雇佣），自动算出**完整度、意向分、漏斗阶段**，
> 汇总进本机轻量库（IndexedDB `alphapath_leads`），并在**独立管理后台**里以 6 个指标 + 漏斗 + 分布 + 趋势 + 可筛选线索表呈现；
> 可导出 CSV / JSON，可带 `?demo=1` 用 36 条**虚构种子数据**给投资人演示（页面常驻 `DEMO DATA` 横幅）。
> 边界照旧说清：**这一版是「本机库」**，跨设备真汇总要等 P1（Workers + D1），方案 §2/§5 已备好。

## 2. 与方案（v0.1）的差异（都已实测，不是偷工）

| 方案原写 | 实施做法 | 原因 |
|---|---|---|
| 线索表 5 张 + 视图（SQLite） | P0 用**单表** `leads`（含 `facts[]` 内嵌） | 静态站没有服务端；P0 的目标是「能看、能演、口径定稿」。P1 落到 D1 时按方案拆表，字段一一对应 |
| 留资率 = 有 ≥3 个结构化字段 | 实现为 **关键字段完整度 ≥75%**（4 个关键字段里有 ≥3 个） | 与「完整度」指标同源，避免两个口径打架；后台卡片上直接写清定义 |
| 未登录也记录（匿名线索） | **未登录不生成线索**，只显示「登录后生成」 | 隐私最小化：没有账号就没有留资主体；实测确认访客不再产生 `anon` 行 |
| 摘要由 LLM 生成 | P0 用**确定性拼装**（身份/日期/受养人/诉求四段） | 现无后端也没有密钥下发通道；P1 接模型时再替换生成器，字段与接口已留好 |
| 联系方式应用层加密 | P0 **不写明文到主字段**：只在用户勾选「同意联系」后写 `contact_email`，另存 8 位短指纹 `email_hash` 用于去重 | 本机库的威胁模型是「同机他人打开 DevTools」，加密密钥无处安放反而制造虚假安全感；P1 上服务端时再加密（方案 §5.3 保留） |

## 3. 数据模型（P0 实存）

存储：**独立 IndexedDB 库** `alphapath_leads`，v1，objectStore `leads`（`keyPath: id`，索引 `stage`）；
无 IndexedDB（Node 测试环境）自动退内存实现，同一套 API。

```js
{
  id: 'ld_<8位djb2>',            // 由 email（小写）或 userId 派生 → 同人恒定，天然幂等
  ext_user_id, email_hash,        // 指纹去重；明文邮箱只在 consent 后进 contact_email
  contact_email, contact_phone,
  display_name,
  identity_type, activation_date, dependants, school_stage, goal, employment,
  intent_score, score_parts: { identity, date, family, goal, engage, contact },
  completeness,                   // 关键字段 4 项占比
  stage,                          // visitor / registered / qualified / contacted / consulting / converted / lost
  consent_at, consent_scope,      // contact / analytics / both
  first_seen_at, last_active_at, n_sessions, n_turns, n_days,
  summary, note,                  // 后台可写跟进备注
  facts: [{ key, label, value, source, confidence, evidence, updated_at }],
  demo: false, created_at, updated_at
}
```

**同步时机**：登录/注册后、每次打开「我的档案」、每轮用户消息（`learnProfile` 之后）、登录态变化后。
同步是 `get(id) → buildLead(prev) → put()`：`created_at` 保留、`updated_at` 刷新、人工阶段（contacted 之后）不回退。

## 4. 评分与阶段（实测数字）

六维（0–100）：身份 20（具体类别）/ 10（笼统）/ 0；激活日 15；家庭 15（受养人 + 学段）/ 8（仅受养人）；
诉求 20（永居）/ 12（续签）/ 10（择校）/ 3（其它）；互动 15（≥8 轮且 ≥2 会话）/ 9（≥4 轮）/ 4（≥1 轮）；
可联系 15（有邮箱且同意）/ 6（仅注册）。

实测样例（同一用户，只勾选「同意联系」前后）：

| 状态 | 身份 | 日期 | 家庭 | 诉求 | 互动 | 可联系 | 总分 | 阶段 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|---|
| 未同意 | 20 | 15 | 15 | 20 | 9 | 6 | **85** | 合格线索 |
| 同意后 | 20 | 15 | 15 | 20 | 9 | 15 | **94** | 合格线索 |

> 完整度 100%（身份/激活日/受养人/诉求全有）。阶段由 `身份 && 激活日 && 分数 ≥50` 判定为合格，
> 之后只能由后台人工推进（已联系 → 跟进 → 成交 / 流失），**自动逻辑不会再把它降级**。

## 5. 管理后台

### 5.1 页面

- **6 个指标卡**：线索总数 / 留资率 / 高意向（≥70）/ 合格及以上 / 平均轮次 / 平均完整度（每张卡都写了口径副标题）
- **转化漏斗**：访客 → 已注册 → 合格线索 → 已联系 → 跟进中 → 已成交（横条 + 人数）
- **身份分布**：甜甜圈（`conic-gradient`，Top5 + 其他）+ 图例
- **诉求分布**：横向条形（拿永居 / 续签 / 择校 / 待确认）
- **近 14 天新增线索**：内联 SVG 折线 + 面积 + 点 + 日期轴
- **线索列表**：称呼（+DEMO 标）/ 身份 / 诉求 / 受养人 / 完整度（迷你条）/ 意向分 / 阶段徽标 / 轮次 / 最近活跃；
  搜索（称呼·身份·诉求·邮箱·学段·摘要）、阶段筛选、三种排序、计数 `n / 总数`
- **详情抽屉**：完整度与意向分仪表 → **结构化字段（每个字段带「原话证据」与来源）** → 摘要 →
  时间线（首次 / 每条事实记录 / 同意 / 最近活跃）→ 改阶段 / 写跟进备注 / 删除该线索 → 私有信息（是否授权联系方式）
- **导出**：当前筛选结果 → CSV（UTF-8 BOM，Excel 直开），列含 18 个字段
- **演示模式**：`?demo=1` 或顶栏按钮 → 36 条虚构线索（固定种子，可重复生成），横幅写明「DEMO DATA…不代表真实用户」，一键可清

## 6. 隐私与合规（P0 能做到的）

| 项 | 做法 |
|---|---|
| 数据在哪 | 只在**本机浏览器**（IndexedDB `alphapath_leads`），无任何网络上传（后台页脚明写） |
| 收什么 | 只有结构化字段 + ≤120 字证据片段；**不存原始对话**（对话仍在 localStorage，且不进线索） |
| 联系方式 | 默认不写；勾选「同意为咨询目的记录我的情况、并接受顾问联系」后才写 `contact_email`，并记 `consent_at/scope` |
| 未登录 | **不生成线索**（不把访客当客户） |
| 我的数据 | 「我的档案 → 导出我的数据」下载 JSON；「删除我的留资」清掉本人线索并把同意复位 |
| 演示数据 | 姓名/邮箱全虚构（`demo100@example.com` 之类），页面常驻 `DEMO DATA` 横幅，避免把演示当真实业绩 |

| 套件 | 结果 |
|---|---|

| `tools/probe_admin.mjs`（本地 8123） | 全项通过，`errs: 0` |
| `tools/probe_admin.mjs`（线上 Pages） | 数值与本地一致，`errs: 0` |
| `tools/probe_acct.mjs`（回归） | 通过，`errs: 0` |
| `tools/probe_contrast.mjs` | 后台浅/深、控制台浅/深：低对比(<3:1) **全 0** |

**顺手修掉的两个真问题**
1. `probe_contrast` 之前从 `el.parentElement` 开始合成背景，会漏掉元素自身的底色 → 把深色底白字的按钮误报成「白底白字」（假阳性）。已改为从元素自身开始逐层合成。
2. 深色主题品牌蓝偏亮，白字对比度只有 **2.63:1**。已将深色下 `.btn.primary` 文字改为深色（约 **7:1**）。

**修掉的一个真 bug**：`syncFrom` 用原始大小写邮箱算 `id`，而 `buildLead` 内部用小写 → 大写邮箱用户会写入 A 键、查到 B 键（同一人变成两条、`created_at` 被重置）。已统一在 `syncFrom` 归一化小写，测试连跑 3 次稳定通过。

## 8. 已知限制（必须如实告诉审核方）

| # | 限制 | 影响 | 何时解决 |
|---|---|---|---|
| 1 | **只能看「这台机器」的库** | 换设备/换浏览器看不到彼此，不能对外宣称「已汇总全量用户」 | P1（Workers + D1） |
| 2 | 演示数据与真实数据同库不同标志 | 若有人不看横幅可能误读 | 横幅 + 行内 DEMO 标 + 导出带「演示数据」列；P1 分库 |
| 3 | 摘要为确定性拼装，不是模型摘要 | 可读性一般 | P1/P3 |
| 4 | 无访问计数（没有埋点） | 「留资率」以完整度为代理，不是「留资人数/访客数」 | P1 加 `page.view` 事件后可算真值 |
| 5 | 评分权重是经验值 | 排序仅供参考，不做自动淘汰 | 后续用真实成交数据回归 |
| 6 | 后台无鉴权 | 谁打开 `admin.html` 都能看本机库 | P1 必须加管理员登录 + 服务端鉴权 |
