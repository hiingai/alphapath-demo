## 0. 一句话结论

> 任务 3 要的三件事（**对话留资 → 汇总成用户信息库 → 管理后台展示**）中，前两件在现有静态站上**做不完整**：
> 静态站没有服务端，账号数据只存在**各用户自己的浏览器**里，无法汇总。
> 建议分两步走：
> **① 立即可交付（0.5–1 天）**：在现有静态站做「留资面板 + 本地用户库 + 管理员视图 + JSON/CSV 导出」，
> 单机即可演示完整故事，投资人看到的是「系统能自动把人变成结构化线索」；
> **② 真汇总（2–3 天）**：加一个**极轻后端**（推荐 Cloudflare Workers + D1/SQLite，免费额度足够），
> 客户端把**结构化事实**（不是聊天原文）批量同步上去，管理后台读真库，得到真实漏斗与分布。
> 关键设计原则：**留资只上报「结构化字段 + 摘要 + 证据」，默认不上报原始对话**——既满足演示价值，也守住合规底线。

## 1. 需求拆解与验收口径

### 1.1 三件事分别是什么

| # | 需求 | 本质 | 验收标准（可测） |
|---|---|---|---|
| A | **对话留资**：根据对话内容动态形成客户结构化数据 | 抽取 + 归并 + 评分 + 漏斗分阶段 | 一段自然对话后，线索出现 ≥5 个字段（身份/激活日/受养人/学段/诉求），每个字段带来源与证据；改口时以新值为准且留痕 |
| B | **汇总所有用户数据形成用户信息库**（轻量数据库） | 多端汇聚 + 去重 + 时间线 | 两台设备/两个账号的线索都能进同一库；同一人重复出现只算一条（幂等去重）；能按时间与维度聚合 |
| C | **管理后台展示**（给投资人看价值） | 概览指标 + 线索列表/详情 + 分布图 + 导出 | 打开即见 6 个核心指标 + 漏斗；可筛选线索并点开看「这个人说过什么、缺什么、值多少」；可导出 CSV |

### 1.2 硬约束（现状决定方案边界）

| # | 约束 | 后果 |
|---|---|---|
| C1 | GitHub Pages **只有静态文件**，无服务端、无数据库 | 「汇总所有用户」在纯前端**不可能**（同源策略 + 无共享存储） |
| C2 | 任务 2 的账号是**本机 IndexedDB**，跨设备不通用 | 汇总必须以「客户端主动上报」为前提，不能靠服务端直接读 |
| C3 | 站点**公开可访问** | 管理后台必须有独立鉴权，且不得把密钥写进静态资源 |
| C4 | 涉及**个人资料**（身份、受养人、学段、联系方式） | 受香港《个人资料（私隐）条例》PDPO 约束：告知、同意、最小化、保留期、查改删 |
| C5 | 投资人演示需要**稳定性** | 演示不能依赖「现场有人注册」；需可复现的种子数据 + 只读演示模式 |
| C6 | 预算敏感（当前零成本） | 优先选免费额度覆盖的方案；D1 免费 5GB / 500 万读/天，Workers 10 万请求/天 |

## 2. 方案选型（三条路，推荐第 2 条）

| 方案 | 做法 | 能真汇总 | 成本 | 工期 | 评价 |
|---|---|:---:|---|---|---|
| **S1 纯前端** | 管理页读本地 IndexedDB + 手动导入 JSON | ✗ | 0 | 0.5–1 天 | 只能演示「单机价值」；适合作为 P0 兜底与 UI 定稿 |
| **S2 Workers + D1**（推荐） | Pages 同域加 `/_api/*`（Worker）+ SQLite(D1)；客户端批量上报结构化事实 | ✓ | 0（免费额度） | 2–3 天 | 轻量、单文件 DB、可导出、免 CORS；与现有 Pages 部署链天然共存 |
| **S3 Supabase** | Postgres + 内置 Auth + 控制台 + RLS | ✓ | 0（500MB 免费） | 2–4 天 | 后台几乎白送，但要重做认证、多一套 SDK；后续若要多端/多角色更省事 |

**推荐 S2，理由**：① SQLite 就是「轻量型数据库」最贴切的答案（单文件、可 `sqlite3 .dump` 交付、投资人也能看懂）；
② 免费额度对演示与早期用户完全够；③ 与现有 GitHub Pages 走同一条部署流水线，不引入第二套账号体系；
④ 认证继续用任务 2 的本机账号，服务端只做「汇聚 + 管理」，**不碰密码**（隐私面最小）。
**保留 S3 作为 Plan B**：若后续要求「管理员在手机上看、多角色、团队协作」，再迁 Supabase，表结构可 1:1 平移。

## 3. 数据模型（S2 版，S1 用同名表存 IndexedDB）

### 3.1 核心表

```sql
-- 线索主表：一人一条（去重后）
CREATE TABLE leads (
  lead_id        TEXT PRIMARY KEY,        -- 服务端生成 ld_xxx
  ext_user_id    TEXT,                    -- 客户端 usr_xxx（匿名时为空）
  email_hash     TEXT,                    -- sha256(lower(email))，用于去重，不存明文
  contact_email  TEXT,                    -- 仅在用户「同意联系」后写入
  contact_phone  TEXT,
  display_name   TEXT,
  identity_type  TEXT,                    -- TTPS_A/B/C / TGPS / ... （与引擎同枚举）
  activation_date TEXT,                   -- ISO 日期
  dependants     INTEGER,
  school_stage   TEXT,
  goal           TEXT,                    -- pr / renewal / school / other
  employment     TEXT,
  intent_score   INTEGER DEFAULT 0,       -- 0–100，见 §4.3
  completeness   INTEGER DEFAULT 0,       -- 0–100，已填字段/关键字段
  stage          TEXT DEFAULT 'visitor',  -- visitor→registered→qualified→contacted→consulting→converted/lost
  consent_at     TEXT, consent_scope TEXT,-- 'contact' / 'analytics' / 'both'
  first_seen_at  TEXT, last_active_at TEXT,
  n_sessions     INTEGER DEFAULT 0,
  n_turns        INTEGER DEFAULT 0,
  n_days         INTEGER DEFAULT 0,
  summary        TEXT,                    -- ≤300 字脱敏摘要
  created_at     TEXT, updated_at TEXT
);
CREATE UNIQUE INDEX idx_leads_email ON leads(email_hash) WHERE email_hash IS NOT NULL;
CREATE INDEX idx_leads_stage ON leads(stage, intent_score DESC);

-- 事实明细（与客户端 facts 同构，保留证据）
CREATE TABLE facts (
  lead_id TEXT, key TEXT, value TEXT,
  confidence REAL DEFAULT 0.6,
  source TEXT,          -- conversation / user / rebuild / admin
  evidence TEXT,        -- 原话片段（≤120 字，脱敏）
  updated_at TEXT, superseded INTEGER DEFAULT 0,
  PRIMARY KEY (lead_id, key, updated_at)
);

-- 事件流：漏斗与审计都靠它
CREATE TABLE events (
  id TEXT PRIMARY KEY,            -- 客户端 event_id（幂等键）
  lead_id TEXT, type TEXT,        -- fact.upsert / lead.stage / session.summary / page.view
  payload TEXT, occurred_at TEXT, received_at TEXT
);

-- 管理员与审计
CREATE TABLE admin_users (id TEXT PRIMARY KEY, email TEXT UNIQUE, role TEXT, created_at TEXT);
CREATE TABLE audit_log (id TEXT PRIMARY KEY, actor TEXT, action TEXT, target TEXT, at TEXT, ip_hash TEXT);

-- 每日物化指标（后台首屏只查这张表，快）
CREATE TABLE daily_metrics (
  day TEXT PRIMARY KEY, users_new INT, leads_new INT, qualified INT, contacted INT,
  converted INT, dau INT, avg_turns REAL, avg_intent REAL
);
```

### 3.2 视图（后台直接用，避免前端算口径）

```sql
CREATE VIEW v_funnel AS
SELECT stage, COUNT(*) n FROM leads GROUP BY stage;
CREATE VIEW v_identity_mix AS
SELECT COALESCE(identity_type,'unknown') k, COUNT(*) n FROM leads GROUP BY 1 ORDER BY n DESC;
CREATE VIEW v_goal_mix AS SELECT COALESCE(goal,'unknown') k, COUNT(*) n FROM leads GROUP BY 1;
CREATE VIEW v_hot AS SELECT * FROM leads WHERE intent_score >= 70 ORDER BY last_active_at DESC;
```

> **为什么不用 MongoDB/宽表**：留资字段是「少而稳定」的（6–10 个），是典型的关系型小表；
> 用 SQLite 意味着**零运维**、可直接 `sqlite3 data.db .dump` 交付客户或做备份，也便于审计口径被复核。

## 4. 「对话留资」怎么算出来（A 项核心）

### 4.1 三层抽取（确定性优先，模型兜底）

| 层 | 手段 | 覆盖字段 | 优点 | 风险控制 |
|---|---|---|---|---|
| L1 确定性规则 | 复用现成 `profile.extract()`（身份别名归一、日期检测、受养人/学段/诉求正则） | 身份、激活日、受养人、学段、诉求、雇佣 | 0 成本、可解释、离线可用、与引擎口径**同一份** | 认不出就不写（宁缺勿错） |
| L2 结构化抽取（可选） | LLM + JSON Schema，只允许输出白名单字段，附 `evidence` 原句与 `confidence` | 预算、时间紧迫度、家庭结构补充、异议点、决策人 | 抓得到自由表达（「明年九月前必须搞定」） | 输出必须过 schema 校验；字段不在白名单直接丢弃；`confidence < 0.6` 只入库不参与评分 |
| L3 人工修正 | 后台「编辑线索」 | 全部 | 兜底准确率 | 写入 `source='admin'`，优先级最高，不被自动覆盖 |

### 4.2 归并与冲突策略（与任务 2 一致，扩展到多人多端）

```
新值 vs 旧值
 ├─ 相等            → 只更新 updated_at
 ├─ 不同且来源优先级更高 → 覆盖，旧值进 history
 ├─ 不同且优先级相同     → 以 occurred_at 更晚者为准，旧的 superseded=1
 └─ 来源=admin          → 永不被自动覆盖（除非 admin 再改）
来源优先级：admin(4) > user(3) > rebuild(2) > conversation(1)
```

- **同一人去重**：`email_hash` 相同 → 合并到同一 `lead_id`；无邮箱 → 以 `ext_user_id` 认；都没有 → 归为匿名线索（只进统计，不进联系列表）。
- **改口留痕**：`facts.history` 保留最近 8 条，后台详情页可看「B 类 → A 类（10-28 改口）」。
- **过期不覆盖结论**：档案是提示，任何资格/日期结论仍由引擎重算（沿用任务 2 的红线）。

### 4.3 线索评分（0–100，先规则后调参）

| 维度 | 满分 | 规则 |
|---|:---:|---|
| 身份明确 | 20 | 具体到类别（高才 A/B/C、优才、专才）20；仅说「高才」10；未知 0 |
| 时间锚点 | 15 | 有激活日 15；有申请日/预计日期 8 |
| 家庭复杂度 | 15 | 受养人 ≥1 且带学段 15；仅受养人 8 |
| 诉求强度 | 20 | 明确「永居」20；「续签」12；「择校」10；泛问 3 |
| 互动深度 | 15 | 轮次 ≥8 且跨 ≥2 个会话 15；≥4 轮 9；1–3 轮 4 |
| 可联系 | 15 | 留邮箱且同意联系 15；仅注册 6 |

`stage` 晋级规则（确定性，不靠模型）：
`visitor` →（注册）`registered` →（身份+激活日齐 + 分数 ≥50）`qualified` →（管理员标记已联系）`contacted` →（标记跟进中）`consulting` →（标记成交）`converted`；任一步可 `lost`（附原因）。

### 4.4 摘要生成（后台详情页用）

- 触发：会话结束（30 分钟无新消息）或每 8 轮，最多每会话 1 次；
- 输入：该会话的**事实 + 用户原话（截断 1.5k 字）**，输出 ≤300 字摘要（诉求 / 现状 / 卡点 / 下一步）；
- 脱敏：邮箱/手机/身份证样式串在送模型前替换为 `[EMAIL]` / `[PHONE]`；
- 存储：只存摘要，**不存原话**（原话仅保留 `evidence` 片段 ≤120 字，用于审核「这条结论从哪来」）。

## 5. 上报与同步（B 项核心）

### 5.1 出站队列（客户端）

```
IndexedDB: outbox(id, type, payload, occurred_at, tries)
  ↑ 留资/评分/阶段变化时写入（同一 lead 同 key 可合并，减少请求）
  ↓ flush(): 批量 POST /_api/ingest（≤50 条），成功即删，失败指数退避(2s→4s→…→5min)
  ↓ pagehide 兜底：navigator.sendBeacon 发最后一批
```

- **幂等**：每条带 `event_id`（uuid），服务端 `INSERT OR IGNORE`；重复投递不产生重复行。
- **离线可用**：演示现场断网也不丢数据，恢复后自动补。
- **默认不传原文**：payload 只含结构化字段 + 证据片段 + 摘要；原始对话**留在本地**（可在设置里开「原文存证」，默认关）。
- **可撤回**：设置页「停止上报」→ 客户端停止 flush 并可请求服务端删除（`DELETE /_api/lead/:id`）。

### 5.2 接口清单（Workers，全部 JSON）

| 方法 | 路径 | 用途 | 鉴权 |
|---|---|---|---|
| POST | `/_api/ingest` | 批量上报（幂等） | 站点匿名 token + HMAC 签名（防刷） |
| POST | `/_api/lead/:id/delete` | 用户请求删除自己的数据 | 同上 + 本人 token |
| POST | `/_api/admin/login` | 管理员登录（邮箱 + 一次性验证码 或 强密码 + TOTP） | — |
| GET | `/_api/admin/overview` | 6 个核心指标 + 漏斗 | admin session（HttpOnly Cookie） |
| GET | `/_api/admin/leads?stage=&q=&sort=` | 线索列表（分页） | admin |
| GET | `/_api/admin/leads/:id` | 详情：事实 + 证据 + 摘要 + 事件时间线 | admin |
| PATCH | `/_api/admin/leads/:id` | 改字段 / 改阶段 / 加跟进备注 | admin + 写 `audit_log` |
| GET | `/_api/admin/export.csv` | 导出（按当前筛选） | admin |
| GET | `/_api/health` | 演示前自检 | — |

### 5.3 安全与隐私（PDPO 对照）

| PDPO 原则 | 落地措施 |
|---|---|
| 收集目的与方式（DPP1） | 注册页勾选「同意为咨询目的记录我的情况」；不勾选仍可用全部功能，仅不进入联系列表 |
| 准确性（DPP2） | 后台可改；`history` 留痕；提供「这不是我说的」一键标记错误 |
| 保留期限（DPP2） | 默认 180 天未活跃 → 自动匿名化（清联系方式、`email_hash` 置空、保留统计） |
| 资料使用（DPP3） | 仅用于咨询与服务匹配；不出售、不做自动决策（评分仅排序，不自动拒绝服务） |
| 保安（DPP4） | 传输 HTTPS；联系方式字段**应用层 AES-GCM 加密**后再入库（密钥在 Worker 环境变量）；管理员登录 TOTP；操作审计 |
| 透明度（DPP5） | 公开「隐私说明」页：收集什么、存哪、多久、怎么删；管理员页面不暴露给公网未授权者 |
| 查阅与更正（DPP6） | 用户侧「导出我的数据（JSON）/ 删除我的数据」按钮；服务端 30 天内响应 |
| 跨境（DPP33） | 若用 Cloudflare 全球边缘，数据可能出境 → 隐私说明中明示；如需本地化，改 Workers 区域提示或换香港主机 |

## 6. 管理后台（C 项核心：投资人看到什么）

### 6.1 页面结构

```
/admin
├── 总览 Overview          ← 演示默认落地页
│   ┌──────────┬──────────┬──────────┬──────────┐
│   │ 累计用户 │ 留资率   │ 高意向   │ 已联系   │
│   │  128     │  64%     │  23      │  11      │
│   └──────────┴──────────┴──────────┴──────────┘
│   ┌───────────────────────┬──────────────────┐
│   │ 漏斗：访客→注册→合格  │ 身份分布（甜甜圈）│
│   │ →已联系→跟进→成交     │ 高才A/B/C/优才…  │
│   └───────────────────────┴──────────────────┘
│   近 30 天：新增线索趋势（折线）+ 平均轮次
├── 线索 Leads             ← 表格：姓名/身份/诉求/分数/阶段/最后活跃；筛选 + 搜索 + 导出 CSV
│   └── 详情：5 项事实（带证据原句）+ 会话摘要 + 事件时间线 + 跟进备注 + 阶段切换
├── 分析 Analytics         ← 诉求分布 / 学段分布 / 激活月份分布 / 卡点 Top5
└── 设置 Settings          ← 管理员、隐私说明、保留期、演示模式开关
```

### 6.2 给投资人的「价值叙事」（指标定义要能自证）

| 指标 | 定义 | 为什么值钱 |
|---|---|---|
| **留资率** | 进入对话的人里，形成 ≥3 个结构化字段的比例 | 证明「聊天即录入」，不需要表单 |
| **合格线索率** | `qualified / registered` | 证明系统能自己判断「谁是有效客户」 |
| **人均对话轮次** | 总会话轮次 / 人数 | 证明有粘性，不是一次性问答 |
| **线索完整度** | 关键字段（身份/日期/受养人/诉求）齐全比例 | 证明可直接交付顾问跟进，不用二次问询 |
| **预估服务价值** | 按身份×受养人×学段的分档模型（内部口径） | 把「线索」翻译成钱，投资人听得懂 |
| **转化漏斗** | 访客→注册→合格→已联系→成交 | 证明闭环可追 |

### 6.3 演示模式（重要）

- 路由 `/admin?demo=1`：读**只读种子库**（30–50 条拟真线索，全名与联系方式均为虚构，页头常驻 `DEMO DATA` 黄条）；
- 真实模式需登录 + 二次确认；
- 目的：现场不依赖网络与他人注册，**且不误导**（明示为演示数据）。

## 7. 分期与工作量

| 期 | 内容 | 产出 | 工作量 |
|---|---|---|---|
| **P0** | 留资面板（现有 console 侧栏）+ 本地用户库 + `admin.html` 读本地/导入 JSON + CSV 导出 + 种子数据 | 单机可完整演示「对话→线索→后台」 | **0.5–1 天** |
| **P1** | Workers + D1 + `/ingest` + 出站队列 + 最小后台（总览/列表/详情） | 真汇总，多设备一条库 | **2–3 天** |
| **P2** | 漏斗与分布图、CSV 导出、跟进状态与备注、审计日志、保留期匿名化 | 可交付运营使用 | **2 天** |
| **P3**（可选） | LLM 摘要与白名单抽取、评分调参、异常留资告警、多管理员角色 | 提升准确率与可运营性 | **2–3 天** |

## 8. 风险与已知限制

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | 静态站无后端，S1 阶段「汇总」是伪汇总 | 若直接对外宣称「已汇总全量用户」= 不实陈述 | 明确区分「演示库 / 真实库」；页头标注数据来源与时间 |
| 2 | 免费额度被刷（`/ingest` 公开） | Worker 配额耗尽、库被灌垃圾 | 匿名 token + HMAC + 每 IP 限速 + payload 大小上限（≤64KB）+ 异常丢弃计数告警 |
| 3 | 联系方式属敏感个资 | 泄露即合规事故 | 应用层加密 + 最小化 + 180 天匿名化 + 审计日志 |
| 4 | LLM 抽取幻觉（编出用户没说的事） | 线索失真、顾问被误导 | 白名单字段 + 必带 `evidence` + `confidence` 门槛 + 后台可一键标记错误 |
| 5 | 演示数据被误当真实数据 | 对投资人构成误导，法律与信誉风险 | 种子数据全虚构 + `DEMO DATA` 常驻标识 + 真实库需登录 |
| 6 | 本地账号体系与后端身份不对齐（换设备 = 新线索） | 同一人重复计数 | `email_hash` 去重；后续可接邮箱验证码做真身份 |
| 7 | 评分模型主观 | 指标被质疑「自己定的」 | 规则全公开、可解释；先做排序用途，不做自动淘汰 |
| 8 | 数据出境（Cloudflare 边缘） | PDPO DPP33 告知义务 | 隐私说明明示 + 可选香港区域主机 |
